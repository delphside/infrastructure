# Hosts: building, networking, keeping current and changing

The hosts: how they are built, reached, kept current and changed.

Each application other than Infrastructure has hosts of its own. Three rules
apply to every step here:

- a step that changes a host, a network rule or a Domain Name System (DNS)
  record is the owner's to run, as a change to production is;
- a read of a host is Claude's by default and the owner's whenever he chooses
  ([programme CLAUDE.md](https://github.com/delphside/programme/blob/main/CLAUDE.md),
  *Deliveries and releases*);
- no host address is recorded in this document or in any application's
  records, which are public: each address is held in the owner's
  `~/.ssh/config` under the host's alias.

An artefact on a host is named as
[1.2 §2.13](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#naming-so-two-lists-can-be-compared)
and
[3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md)
say.

| Task | Section |
| --- | --- |
| find a host's alias, shape or system | [The hosts](#the-hosts) |
| build a host | [Building a host](#building-a-host) |
| find a port rule or a DNS record | [Networking](#networking) |
| upgrade packages or reboot | [Upgrading and rebooting](#upgrading-and-rebooting), made as [Making a host change](#making-a-host-change) says |
| change a DNS record or a port rule | [Making a host change](#making-a-host-change) |
| find an artefact on a host or in the console | [3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md) |

## The hosts

All are virtual machines in Oracle Cloud Infrastructure (OCI), inside the
Always Free allowance. An *OCPU* is Oracle's unit of CPU: one physical core.

| Host | Application | `ssh` alias | Shape | Architecture | System | Region | Swapfile |
| --- | --- | --- | --- | --- | --- | --- | --- |
| production | Tile Lite Elite | `tile-lite-elite` | `VM.Standard.E2.1.Micro`: 1 OCPU, 1 GB | x86_64 | Ubuntu 24.04 LTS | `uk-cardiff-1` | 2,047 MB |
| rehearsal | Tile Lite Elite | `tile-lite-elite-rehearsal` | `VM.Standard.E2.1.Micro`: 1 OCPU, 1 GB | x86_64 | Ubuntu 24.04 LTS | not recorded | yes: size not recorded |
| production | Dark Portal | `dark-portal` | `VM.Standard.A1.Flex`: 1 OCPU, 6 GB, burstable off | aarch64 | Ubuntu 26.04 LTS Minimal | `uk-cardiff-1` | no: not needed at 6 GB |
| non-production | Dark Portal | `dark-portal-nonprod` | `VM.Standard.A1.Flex`: 3 OCPU, 18 GB | aarch64 | Ubuntu 26.04 LTS Minimal | not recorded | not recorded |

Tile Lite Elite's hosts are x86_64, so that images built on an x86_64 machine
run unchanged. Each host has a Secure Shell (SSH) key of its own, named in
[3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#ssh-keys).
The private half stays in `~/.ssh`.

Which hosts an application runs on is the `[hosts.*]` tables of its
`app-profile.toml`. A *pair* is a host that names another in its `compare_with`
key, and the host it names: rehearsal with production, and Dark Portal's
non-production host with its production host. Step 2 of
[Making a host change](#making-a-host-change) says which of a pair is changed
first.

## Building a host

Building a host is a host change, made as
[Making a host change](#making-a-host-change) says.

The owner builds the host in the OCI console, then over SSH with
`ssh <alias>`. A step that differs between hosts says so, and the table in
[The hosts](#the-hosts) gives the values.

1. **Sign up** at `cloud.oracle.com`, once. Phone and card verification is an
   identity check only.
2. **Upgrade to Pay-As-You-Go before creating the first instance, and set a
   budget.** Oracle reclaims idle Always Free instances (95th-percentile CPU
   and network use both under 20% over seven days), which a quiet host is.
   Staying within the Always Free limits costs nothing, and Pay-As-You-Go bills
   anything beyond them, so the account carries a monthly budget with an alert
   at 100%. The owner rechecks Oracle's policy at each build.
3. **Check the allowance left**, in the console:
   - *Compute → Instances*: Ampere A1 instances share 4 OCPU and 24 GB, and
     the allowance is two `VM.Standard.E2.1.Micro` instances, both in use by
     Tile Lite Elite;
   - *Storage → Boot volumes* and *Block volumes*: all volumes share 200 GB,
     so the sizes with the new boot volume must total at most that.
4. **Make the host's SSH key**, on the owner's machine, named as
   [3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#ssh-keys)
   names it:

   ```bash
   ssh-keygen -t ed25519 -f ~/.ssh/<key name> -C <alias>
   ```

5. **Create the instance** (*Compute → Instances → Create instance*):
   - image and shape: the host's row in the table (on an A1 shape,
     burstable performance off, for whole cores);
   - a public subnet and a public IPv4 address;
   - the public half of the host's key, pasted in;
   - the default boot volume, about 47 GB on A1 and on a Micro.
6. **Point the ssh alias at the new address**: add an entry to
   `~/.ssh/config`, or set `HostName` in the existing one. Tile Lite Elite's
   setup script leaves an existing entry unchanged.

   ```text
   Host <alias>
       HostName <public IP>
       User ubuntu
       IdentityFile ~/.ssh/<key name>
   ```

   Check that `ssh <alias> 'uname -m && lsb_release -ds'` prints the host's
   architecture and system.
7. **Open the network**, as [Networking](#networking) says.
8. **Install Docker and add a swapfile**, over `ssh <alias>`:
   - Docker Engine and the Compose plugin from Docker's apt repository, as
     [Docker's Ubuntu guide](https://docs.docker.com/engine/install/ubuntu/)
     gives it;
   - on a Minimal image, `ca-certificates` and `curl` installed first, to
     fetch Docker's key;
   - where Docker's repository has no release for the system yet, Ubuntu's
     `docker.io` and `docker-compose-v2` instead;
   - `sudo usermod -aG docker ubuntu`, because Tile Lite Elite's deploy scripts
     run `docker` without `sudo`, then log out and back in;
   - on a host with a swapfile in the table, a swapfile of the size the table
     gives, for headroom on 1 GB, persisted in `/etc/fstab`;
   - where the table does not record the size, the size of the pair's swapfile,
     which `swapon --show` reads on that host, or none where the pair has none.
     The owner tells Claude the size, and Claude records it in the *Swapfile*
     column of the table in [The hosts](#the-hosts) and clears the host's entry
     under
     [Not yet recorded](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#not-yet-recorded)
     in 3.3.2 (delphside/infrastructure#10 *Record the hosts as built in
     3.3.2*).

   The commands:

     ```bash
     sudo fallocate -l <size> /swapfile && sudo chmod 600 /swapfile
     sudo mkswap /swapfile && sudo swapon /swapfile
     echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
     ```

9. **Install what every host needs**:
   - `sudo apt-get install -y jq`, for Tile Lite Elite's log commands;
   - `sudo apt-get install -y unattended-upgrades`, a no-op where the image
     already has it ([Keeping the hosts current](#keeping-the-hosts-current)).

   Check steps 8 and 9:

   ```bash
   ssh <alias> 'docker run --rm hello-world'                  # "Hello from Docker!"
   ssh <alias> 'free -h && nproc'                             # memory; nproc counts threads
   ssh <alias> 'jq --version'                                 # a version
   ssh <alias> 'systemctl is-enabled unattended-upgrades'     # enabled
   ```

10. **On Tile Lite Elite's production host only, install the journald
    drop-ins**, `50-cap.conf` and `zz-tile-lite-elite.conf`, in
    `/etc/systemd/journald.conf.d/`, with the values in
    [3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#the-hosts).
11. **Tell Claude, in the host's work package, the shape, architecture,
    system, region, boot volume size and swapfile size**, and Claude records the
    host as step 5 of [Making a host change](#making-a-host-change) says, and in
    the application's capacity plan, which takes it in the next plan
    ([3.1.3](https://github.com/delphside/programme/tree/main/applications/tile-lite-elite/3.1.3-capacity-plan),
    [3.2.3](https://github.com/delphside/programme/tree/main/applications/dark-portal/3.2.3-capacity-plan)).

The application's own stack, its `.env`, jobs, first deploy and HTTPS, is built
afterwards as the application's own document says: Tile Lite Elite's
[4.3.8](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.8-building-and-maintaining-a-host.md#building-a-host).
Dark Portal has none yet.

## Networking

### The domain and its DNS records

`tileliteelite.com` is registered at GoDaddy, which also holds its DNS records.
The records:

| Name | Type | Points at | For |
| --- | --- | --- | --- |
| `tileliteelite.com` | A | Tile Lite Elite's production host | the application |
| `www` | CNAME | the root domain | the application |

The rest of the domain's records are listed as not recorded in
[3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#not-yet-recorded).
A change to a record is a host change, made as
[Making a host change](#making-a-host-change) says.

Which comes first, a new record or the application's HTTPS name, is the
application's own: Tile Lite Elite's is in its
[4.3.8](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.8-building-and-maintaining-a-host.md#https).
Dark Portal has no name: it is private.

### The subnet's security list

The security list attached to a host's subnet decides what reaches the host
from the internet. The rules the hosts need:

| Direction | Rule | For |
| --- | --- | --- |
| ingress | TCP 22 | SSH, every host |
| ingress | TCP 80 and 443, UDP 443 | Tile Lite Elite's web server, Caddy |
| egress | all | DNS, `apt-get`, image pulls and the Blizzard API |

Each of these is needed for the rules to work, and a missing one shows only
as a timeout:

- the subnet needs a route to an internet gateway;
- the rules go in the security list attached to the subnet (*Subnet →
  Security*), not the security group the instance's *Networking* tab creates,
  which has no inbound rules, and not the instance's own *Security* tab, which
  is Secure Boot;
- egress is all, because a TCP-only rule blocks DNS, and with it `apt-get` and
  image pulls.

A virtual cloud network made by the create wizard already allows TCP 22 and all
egress, so a host that serves only SSH needs no network change; a Tile Lite
Elite host still needs the ports in the table.

A list that allows ports 80 and 443 opens them to every host on its subnet, so
what a host answers on them is decided on the host: Dark Portal's production
host listens on neither, so it answers on SSH only although the list allows
more.

[3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#oracle-cloud-and-the-domain)
records the `oci-dev-tools-vcn` list as built and, in
[its hosts table](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#the-hosts),
Tile Lite Elite production's `iptables` `INPUT` chain. Tile Lite Elite's subnet
and list and the other hosts' `iptables` rules are
[not yet recorded](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#not-yet-recorded).

### Reaching an application

| Application | How it is reached |
| --- | --- |
| Tile Lite Elite | publicly, over HTTPS on its domain, through the reverse proxy it publishes on 80 and 443 |
| Dark Portal | privately, over SSH only |

## Keeping the hosts current

| Layer | Updated by | Who acts | Cadence |
| --- | --- | --- | --- |
| security updates to OS packages | `unattended-upgrades` | nobody (automatic) | daily (`apt-daily-upgrade.timer`) |
| other OS packages, Docker included | `apt`, a host change ([Making a host change](#making-a-host-change)) | the owner | when needed |
| the running kernel and libc | a reboot, a host change ([Making a host change](#making-a-host-change)) | the owner | when `/var/run/reboot-required` appears |

An application keeps its own layers, its images, libraries and release: Tile
Lite Elite's are in its
[4.3.8](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.8-building-and-maintaining-a-host.md#keeping-the-application-current).

**`unattended-upgrades` installs updates and reboots nothing**, so a kernel or
libc fix is live only after a reboot. The programme's
`scripts/board/board-hosts.py` reads the hosts each application's
`app-profile.toml` lists under `[hosts.*]`, over `ssh`, read-only:

- it reads, on each host, the running and the newest installed kernel, the
  reboot flag, the packages waiting, the Docker version and how long since
  automatic updates last succeeded;
- it reports a reboot pending, a newer kernel not running, packages waiting
  that automatic updates do not install (security ones install themselves),
  automatic updates that have stopped and a kernel or Docker version that
  differs from its pair;
- it counts packages from the host's last daily `apt update`; a phased package
  such as `netplan.io` (which Ubuntu releases gradually) counts once the host
  is in its phase.

An application's own tooling can call it: Tile Lite Elite's use is in its
[4.3.8](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.8-building-and-maintaining-a-host.md#keeping-the-application-current).
The same read runs weekly as the programme's `host-currency` activity, which
raises a host maintenance work package in `delphside/infrastructure` for each
change a host owes: an upgrade, a reboot, a repair or levelling drift from its
pair
([programme 1.4](https://github.com/delphside/programme/blob/main/docs/1.4-programme-activities.md)).

### Upgrading and rebooting

**A package upgrade and a reboot are separate deliveries**
([1.2 §2.2.1](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#221-business-as-usual-updates)),
the upgrade first, so the reboot picks up any kernel it installs. A reboot is an
outage; the containers restart with the host (`restart: unless-stopped`).

The upgrade:

```bash
sudo apt-get update && sudo apt-get dist-upgrade
```

The reboot:

```bash
sudo reboot
```

## Making a host change

A host or network change is Infrastructure's `Other` delivery
([programme 1.2 §2.15](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#host-maintenance-is-the-infrastructure-applications)):
a work package in `delphside/infrastructure`, a date milestone `YYYY.MM.DD-n`,
and a row in Infrastructure's delivery log
([3.3.1](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.1-delivery-log.md)).
It covers:

- building a host;
- a package upgrade, Docker's included;
- a reboot;
- a setting made on the host by hand, such as a journald cap or a firewall
  rule;
- a rule in the subnet's security list;
- a DNS record.

**It has no CI, gate, smoke test or scripted rollback**, so the owner reviews
and tests it by hand. The steps, in this order, say who acts:

1. **Claude raises the work package**, which `host-currency` does for what a
   host owes.
2. **The owner starts on the host that names the other, where the host has a
   pair**: rehearsal, or Dark Portal's non-production host
   ([1.2 §2.15](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#host-maintenance-is-the-infrastructure-applications)).
   Two cases differ:
   - a rule in the subnet's security list or a DNS record reaches every host on
     the subnet or name, so it is made once, and then each application on it
     verifies itself; `board-hosts.py` does not apply;
   - a new host has no pair step: `board-hosts.py` and the application's first
     deploy check it.
3. **Whoever can read it notes what the change replaces**: Claude where it can
   reach the host, the owner for a console setting or a DNS record Claude
   cannot read. For a package, the note in the work package is what
   `apt list --upgradable` lists on the host as of the last daily update, and
   the owner adds anything more the upgrade installs. For a setting or a
   record, it is its current value.
4. **The owner makes the change**, with the commands of
   [Upgrading and rebooting](#upgrading-and-rebooting) for a package or a
   reboot, on the first host of the pair (step 2). Claude verifies the
   application on it
   ([How an application verifies itself](#how-an-application-verifies-itself)),
   and on Tile Lite Elite's rehearsal host the local session also runs the
   regression suite. Once those pass, the owner makes the same change on the
   other host. Claude runs the checks that
   [the test approach](#the-test-approach-for-a-host-delivery) gives it, the
   pair's agreement included, and verifies the application on the other host.
5. **Claude records it**. A package upgrade or a reboot is recorded in its work
   package only; any other change goes where this table says, and clears the
   matching entry under
   [Not yet recorded](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#not-yet-recorded)
   in 3.3.2 where there is one:

   | What | Recorded in |
   | --- | --- |
   | what a host is and needs: its shape, architecture, system, region and swapfile size, a DNS record, a security-list rule it needs | the tables of this document |
   | as built: the security list, an `OCI compute` row with its region and boot volume, a file, a setting, a firewall rule | [3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md) |

6. **The local session makes the milestone for the day the change landed and
   writes the delivery-log row with it**, as one act
   ([1.2](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#11-what-a-milestone-says)).
   The local session then closes the work package and the milestone by hand: no
   deploy settles an `Other` delivery's milestone
   ([1.2](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#a-delivery-that-ships-no-application-code)).

### The test approach for a host delivery

Each host change's test approach is the same, with the pair, subnet, DNS and
new-host cases as step 2 gives them:

- `board-hosts.py` afterwards reports nothing owed for that change, and the
  pair agrees;
- the application on the host verifies itself, as a box for Claude in the work
  package's technical tests, trusting the exit status;
- on Tile Lite Elite, after each change made on rehearsal first (step 2's
  pair case), whatever it changes, the regression suite passes on rehearsal
  before production is changed. It is a box for Claude, run from the local
  session, in the work package's technical tests. The suite runs against
  whatever rehearsal runs at the time, with
  [4.3.3 §1.5.3](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.3-testing-ci-and-release.md#153-regression-on-rehearsal-then-judge-it)'s
  commands only: `rehearsal-limits.sh regression`, the suite, then
  `rehearsal-limits.sh production`, always, even when the suite fails. The
  suite is cheap, and rehearsal is the change's last check before production.
