# Hosts: building, networking and keeping them current

The hosts: how they are built, reached and kept current, and changed.

Each application has hosts of its own: no host is shared. Every host step here
is the owner's to run ([CLAUDE.md](../CLAUDE.md)). No host address is recorded
in this document or in Infrastructure's records, nor in any application's: the
repositories are public, so each address is held in the owner's `~/.ssh/config`
under the host's alias.

| build a host | [Building a host](#building-a-host) |
| find a port rule or a DNS record | [Networking](#networking) |

## The hosts

All are virtual machines in Oracle Cloud Infrastructure (OCI), inside the
Always Free allowance. An OCPU is Oracle's unit of CPU: one physical core.

| Host | Application | `ssh` alias | Shape | Architecture | System | Region | Swapfile |
| --- | --- | --- | --- | --- | --- | --- | --- |
| production | Tile Lite Elite | `tile-lite-elite` | `VM.Standard.E2.1.Micro`: 1 OCPU, 1 GB | x86_64 | Ubuntu 24.04 LTS | `uk-cardiff-1` | 2,047 MB |
| rehearsal | Tile Lite Elite | `tile-lite-elite-rehearsal` | `VM.Standard.E2.1.Micro`: 1 OCPU, 1 GB | x86_64 | Ubuntu 24.04 LTS | not recorded | yes: size not recorded |
| production | Dark Portal | `dark-portal` | `VM.Standard.A1.Flex`: 1 OCPU, 6 GB, burstable off | aarch64 | Ubuntu 26.04 LTS Minimal | `uk-cardiff-1` | no: not needed at 6 GB (the build runbook of delphside/dark-portal#6) |
| non-production | Dark Portal | `dark-portal-nonprod` | `VM.Standard.A1.Flex`: 3 OCPU, 18 GB as built, 2 OCPU and 12 GB once shrunk | aarch64 | Ubuntu 26.04 LTS Minimal | not recorded | not recorded |

Tile Lite Elite's hosts are x86_64, so that images built on an x86_64 machine
run unchanged. Each host has an SSH key of its own, named in
[3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#ssh-keys).

The private half of a key stays in `~/.ssh`, and the public half is pasted
into the instance at creation. A host's key is its own, so losing one opens no
other host.

Which hosts an application owns is the `[hosts.*]` tables of its
`app-profile.toml`. A **pair** is a host that names another in its
`compare_with` key, and the host it names: rehearsal with production, and Dark
Portal's non-production host with its production host. A change is made on the
host that names the other first.

## Building a host

Building a host is Infrastructure's `Other` delivery, made as
[Making a host change](#making-a-host-change) says: a work package in
`delphside/infrastructure`, a date milestone and a row in
[3.3.1](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.1-delivery-log.md).

The owner builds the host in the OCI console, then over Secure Shell (SSH) with
`ssh <alias>`. A step that differs between hosts says so, and the table in
[The hosts](#the-hosts) gives the values.

1. **Sign up** at `cloud.oracle.com`, once. Phone and card verification is an
   identity check, not a charge.
2. **Upgrade to Pay-As-You-Go before creating the first instance, and set a
   budget.** Oracle reclaims idle Free-tier instances (95th-percentile CPU
   under 20% over seven days), which a quiet host is. Staying within the Always
   Free limits costs nothing, and Pay-As-You-Go bills anything beyond them
   instead of refusing it, so the account carries a monthly budget with an
   alert at 100%. The owner rechecks Oracle's policy at each build.
3. **Check the allowance left**, in the console:
   - *Compute → Instances*: Ampere A1 instances share 4 OCPU and 24 GB;
   - *Storage → Boot volumes* and *Block volumes*: all volumes share 200 GB,
     so the sizes with the new boot volume must total at most that.
4. **Make the host's SSH key**, on the owner's machine, named as
   [3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#ssh-keys)
   names it:

   ```bash
   ssh-keygen -t ed25519 -f ~/.ssh/<key name> -C <alias>
   ```

5. **Create the instance** (*Compute → Instances → Create instance*):
   - image and shape: the host's row in the table (on an A1 shape,
     burstable performance off, for whole cores);
   - a public subnet and a public IPv4 address;
   - the public half of the host's key, pasted in;
   - the default boot volume, about 47 GB on A1.
6. **Point the ssh alias at the new address**: add an entry to
   `~/.ssh/config`, or set `HostName` in the existing one. A setup script of
   an application does not rewrite an entry that exists.

   ```text
   Host <alias>
       HostName <public IP>
       User ubuntu
       IdentityFile ~/.ssh/<key name>
   ```

   Check that `ssh <alias> 'uname -m && lsb_release -ds'` prints the host's
   architecture and system.
7. **Open the network**, as [Networking](#networking) says.
8. **Install Docker and add a swapfile**, over `ssh <alias>`:
   - Docker Engine and the Compose plugin from Docker's apt repository, as
     [Docker's Ubuntu guide](https://docs.docker.com/engine/install/ubuntu/)
     gives it. A Minimal image needs `ca-certificates` and `curl` installed
     first, to fetch Docker's key. Where Docker's repository has no release for
     the system yet, use Ubuntu's `docker.io` and `docker-compose-v2`;
   - `sudo usermod -aG docker ubuntu`, because the applications' deploy scripts
     run `docker` without `sudo`, then log out and back in;
   - on a host with a swapfile in the table, a swapfile of the size the table
     gives, for headroom on 1 GB, persisted in `/etc/fstab`:

     ```bash
     sudo fallocate -l <size> /swapfile && sudo chmod 600 /swapfile
     sudo mkswap /swapfile && sudo swapon /swapfile
     echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
     ```

9. **Install what every host needs**:
   - `sudo apt-get install -y jq`, for the applications' log commands;
   - `sudo apt-get install -y unattended-upgrades`, a no-op where the image
     already has it ([Keeping the hosts current](#keeping-the-hosts-current)).

   Check them:

   ```bash
   ssh <alias> 'docker run --rm hello-world'                  # "Hello from Docker!"
   ssh <alias> 'free -h && nproc'                             # the shape's memory and cores
   ssh <alias> 'systemctl is-enabled unattended-upgrades'     # enabled
   ```

10. **On Tile Lite Elite's production host only, install the journald
    drop-ins**, `50-cap.conf` and `zz-tile-lite-elite.conf`, in
    `/etc/systemd/journald.conf.d/`, with the values in
    [3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#the-hosts).
11. **Tell Claude, in the host's work package, the region, the image and the
    volume size**, and Claude records the host in
    [3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md)
    and the application's capacity plan.

The application's own stack, its `.env`, jobs, first deploy and HTTPS, is built
on the host afterwards, in the application's own document: Tile Lite Elite's
[4.3.4](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.4-production-environment.md#building-a-host).
Dark Portal's, once written, is in
[its repository](https://github.com/delphside/dark-portal).

## Networking

### The domain and its DNS records

`tileliteelite.com` is registered at GoDaddy, which also holds its Domain Name
System (DNS) records. The records recorded so far:

| Name | Type | Points at | For |
| --- | --- | --- | --- |
| `tileliteelite.com` | A | Tile Lite Elite's production host | the application |
| `www` | CNAME | the root domain | the application |

The rest of the domain's records are not yet recorded
([3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md#not-yet-recorded)).
A change to a record is a host change, made as
[Making a host change](#making-a-host-change) says.

The order of a new record and the application's HTTPS name is the
application's own: Tile Lite Elite's is in its
[4.3.4](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.4-production-environment.md#building-a-host).
Dark Portal has no name: it is private.

### The subnet's security list

The security list attached to a host's subnet decides what reaches the host
from the internet. The rules wanted:

| Direction | Rule | For |
| --- | --- | --- |
| ingress | TCP 22 | SSH, every host |
| ingress | TCP 80 and 443, UDP 443 | Tile Lite Elite's web server, Caddy |
| egress | all | DNS, `apt-get`, image pulls and the Blizzard API |

Failures show only as timeouts:

- the subnet needs a route to an internet gateway;
- the rules go in the security list attached to the subnet (*Subnet →
  Security*), not the security group the instance's *Networking* tab creates,
  which has no inbound rules, and not the instance's own *Security* tab, which
  is Secure Boot;
- egress is all, because a TCP-only rule blocks DNS, and with it `apt-get` and
  image pulls;
- a virtual cloud network (VCN) made by the create wizard already allows TCP
  22 and all egress, so where `ssh` connects, the network needs no change.

A list that allows ports 80 and 443 opens them to every host on its subnet, so
what a host answers on them is decided on the host. Dark Portal's production
host listens on neither, and Oracle's Ubuntu image firewall allows only 22, so
it answers on SSH only although the list allows more (the build runbook of
delphside/dark-portal#6). The list and the hosts' own firewalls are in
[3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md).

### Reaching an application

| Application | How it is reached |
| --- | --- |
| Tile Lite Elite | publicly, over HTTPS on its domain, through the reverse proxy it publishes on 80 and 443 |
| Dark Portal | privately: an SSH tunnel from the owner's machine over its alias, so nothing needs a certificate |

## Keeping the hosts current

| Layer | Updated by | Who acts | Cadence |
| --- | --- | --- | --- |
| security updates to OS packages | `unattended-upgrades` | nobody (automatic) | daily (`apt-daily-upgrade.timer`) |
| other OS packages, Docker included | `apt`, a host change ([Making a host change](#making-a-host-change)) | the owner | when needed |
| the running kernel and libc | a reboot, a host change ([Making a host change](#making-a-host-change)) | the owner | when `/var/run/reboot-required` appears |

An application keeps its own layers, its images, libraries and release: Tile
Lite Elite's are in its
[4.3.4](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.4-production-environment.md#keeping-the-application-current).

**`unattended-upgrades` installs and never reboots**, so a kernel or libc fix
is not live until a reboot. The programme's `scripts/board/board-hosts.py`
reads the hosts each application's `app-profile.toml` lists under `[hosts.*]`,
over `ssh`, read-only:

- it reads, on each host, the running and the newest installed kernel, the
  reboot flag, the packages waiting, the Docker version and how long since
  automatic updates last succeeded;
- it reports a reboot pending, a newer kernel not running, packages waiting
  that automatic updates do not install (security ones install themselves),
  automatic updates that have stopped and a kernel or Docker version that
  differs from its pair;
- it counts packages from the host's last daily `apt update`; a phased package
  such as `netplan.io` (which Ubuntu releases gradually) counts once this host
  is in its phase.

An application's own tooling may call it: Tile Lite Elite's use is in its
[4.3.4](https://github.com/delphside/tile-lite-elite/blob/main/docs/4.3.4-production-environment.md#keeping-the-application-current).
The same read runs weekly as the programme's `host-currency` activity, which
raises a host maintenance work package in `delphside/infrastructure` for each
change a host owes: an upgrade, a reboot, a repair or levelling drift from its
pair
([programme 1.4](https://github.com/delphside/programme/blob/main/docs/1.4-programme-activities.md)).

### Upgrading and rebooting

**A package upgrade and a reboot are separate deliveries**
([1.2 §2.2.1](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#221-business-as-usual-updates)),
the upgrade first, so the reboot picks up any kernel it installs. A reboot is an
outage; the containers restart with the host (`restart: unless-stopped`).

The upgrade:

```bash
sudo apt-get update && sudo apt-get dist-upgrade
```

The reboot, when `/var/run/reboot-required` appears:

```bash
sudo reboot
```

## Making a host change

A host or network change is Infrastructure's `Other` delivery
([programme 1.2 §2.15](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#host-maintenance-is-the-infrastructure-applications)):
a work package in `delphside/infrastructure`, a **date** milestone
`YYYY.MM.DD-n`, set the day it lands and never a letter, and a row in
Infrastructure's delivery log
([3.3.1](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.1-delivery-log.md)).
It covers building a host, a package upgrade, Docker's, a reboot, a setting
made on the host by hand (a journald cap or a firewall rule), a rule in the
subnet's security list and a DNS record.

**It has no CI, gate, smoke test or scripted rollback, so the owner reviews and
tests it by hand.** The owner makes it, in this order:

1. **Raise the work package**, which `host-currency` does for what a host owes.
2. **Where the host has a pair, make the change on the host that names the
   other first**: rehearsal, or Dark Portal's non-production host
   ([1.2 §2.15](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#host-maintenance-is-the-infrastructure-applications)).
   A rule in the subnet's security list or a DNS record reaches every host on
   the subnet or name, so it is made once, and then each application on it
   verifies itself; `board-hosts.py` does not apply. A new host has no pair
   step: `board-hosts.py` and the application's first deploy check it.
3. **Keep what is replaced.** For a package, note in the work package what
   `sudo apt-get update && apt list --upgradable` lists on the host. For a
   setting or a record, note its current value.
4. **Make the change**, with the commands of
   [Upgrading and rebooting](#upgrading-and-rebooting) for a package or a
   reboot, then test it as the next section says, then make the same change on
   the other host of the pair.
5. **Record it.** A change to a file, setting, rule or record is recorded in
   [3.3.2](https://github.com/delphside/programme/blob/main/applications/infrastructure/3.3.2-artefacts.md);
   a package upgrade or a reboot is recorded in its work package only. Write the
   delivery-log row.
6. **Set the milestone to the day it landed and close the work package by
   hand**: no deploy settles an `Other` delivery's milestone
   ([1.2](https://github.com/delphside/programme/blob/main/docs/1.2-change-lifecycle.md#a-delivery-that-ships-no-application-code)).

### The test approach for a host delivery

Each host change's test approach is the same:

- where the host has a pair, the change is made on the host that names the
  other first, then on the other;
- `board-hosts.py` afterwards reports nothing owed for that change, and the
  pair agrees;
- the application on the host verifies itself, as a box for Claude in the work
  package's technical tests, trusting the exit status;
- a subnet rule or a DNS record is made once and then verified by each
  application it reaches, and `board-hosts.py` does not apply;
- a new host is checked by `board-hosts.py` and the application's first deploy,
  with no pair step.

### How an application verifies itself

No trigger is automated: a host change is made by hand, so its verification is
a step of it.

| Application | Its verification |
| --- | --- |
| Tile Lite Elite | `scripts/deliver/verify.sh` |
| Dark Portal | its own, once its first release builds one; until then the host read and an SSH login |
